nday: Building the Patch-Diffing Pipeline Attackers Already Run

I combined Google's report on agentic n-day exploitation with Anthropic's always-on agent pattern into a pipeline that watches open-source commits, catches silent security fixes, and tries to exploit and get around each one

Introduction

TL;DR Attackers already run agents that diff upstream patches and turn them into working exploits. nday is a defender’s version of that loop: it watches an open-source repository’s commits, flags security fixes (including silent ones with no advisory), spins up a disposable cloud VM to build the vulnerable and fixed versions, proves each fix with a live exploit, and then tries to bypass it or hit unpatched variants. Across runs on an open-source Java identity server, nday confirmed eight security fixes by live exploit, including one silent fix with no CVE, and proved that two of those patches were incomplete.

Individually, none of the pieces inside nday are new, though wiring them together turned up some interesting engineering problems: keeping credentials away from untrusted builds, forcing every agent to prove its claims against fresh servers, and building evals so triage neither wastes hours on noise nor quietly drops real bugs.

If you publish code (an open-source project, a public SDK, a self-hosted product), anyone can point this loop at your commit history. Running it yourself means finding out whether a fix holds, and whether a sibling code path is still open, before someone else does. If you mostly run third-party software, this is the clock your patching and SOC are racing against.

I am not naming the projects here. The main target is an open-source identity and access management server written in Java, and I also built classifier evals against a Python web framework, a self-hosted Go Git service, and a wider set of public repositories.

Where the Idea Came From

Google’s post, Agentic Threat Activity Crosses a Significant Threshold, came out on November 16, 2026. One framework it describes, found on an exposed staging server and named exploit_agent, was “set up to conduct continuous differential analysis of popular web application software.” It “compares code before and after patch announcements,” then drafts exploits and executes them without human intervention.

The same post lays out both sides of the problem defenders face. For one print management product, researchers “generated working exploits for the vulnerabilities within a day of disclosure.” At the same time, after another patch, “hundreds of claimed but non-functional POCs, likely generated with the help of LLMs, were published.” That second observation shaped almost every verification gate in nday: a defender-side pipeline that emits plausible-sounding but broken PoCs just adds to the noise.

Three days earlier, on November 13, Anthropic published Building always-on agents. It breaks an unattended agent down into “five core primitives: an event inbox, timers, memory, permissions, and an outbox.” External sources drop events into an inbox “where a worker picks it up,” and each run wakes the agent up to finish one job and persist the result. Memory lives in plain files with an index and “should only hold what the agent can’t look up again.” An optional “dreaming” pass reviews past sessions to curate those notes.

What Is a Silent Fix?

Patch-diffing pipelines like exploit_agent target n-days, which are vulnerabilities that are already fixed upstream. The exposure window starts the moment a fix lands in git and closes only when a deployment picks it up. Relying on advisory feeds leaves you blind during part of that window, because plenty of security fixes land weeks before an advisory, or never get one at all.

A silent fix is a commit that closes a real security bug in the project’s own code with no CVE or advisory attached. The commit message usually reads like routine maintenance or just an issue reference. Three real examples from the commits nday’s classifier was evaluated on:

  • An unescaped delimiter in a cache key that let two identities collide, returning the wrong user on lookup.
  • Uploaded attachments that were never checked to belong to the repository they were attached to.
  • An HTML sanitizer that was silently skipped whenever the input parsed as valid JSON.

None of those messages mention security. You only catch them by reading the diff, which an agent can do on every commit as long as the classifier judges the code rather than the message.

The Architecture

nday is a Go service built around Anthropic’s always-on pattern. Each new commit or rebase-merged PR lands in an inbox as an event, a worker claims it, and the run moves through nine steps:

nday’s architecture. The agents and their logins stay on the Mac, each classified run gets its own boat VM, and the numbers follow one run’s steps.

Every phase transition is checkpointed in Postgres. If a worker crashes or a VM dies mid-run, the next worker picks up from the last saved checkpoint rather than repeating finished model calls or builds. The allowed transitions live in a single Go table mirrored by a Temporal Logic of Actions (TLA+) spec built with pstack, and the test suite fails if the two ever drift apart.

Because compiling a large repository twice and building CodeQL databases takes 40 to 50 minutes per run, steps 2 and 3 act as a fast funnel on my Mac before any cloud VM is forked. Only commits that survive triage get built, and only fixes confirmed by nday’s own exploit rerun and judge move on to blast-radius and bypass testing. Everything else goes straight to the report.

How the Always-On Plumbing Works

Because I do not own the repositories I watch, nday does not rely on webhooks or API tokens. On a 10-minute timer (--poll), it runs git fetch --prune --no-tags into a local bare mirror, walks new first-parent commits on the default branch, groups rebase-merged PRs into a single change, and deduplicates events by repo and commit. Two other timers handle cleanup and memory curation: an orphan-VM sweep every 15 minutes (--sweep) and a daily dreaming pass (--dream). One triage worker on the Mac drains incoming events, while a pool of VM workers claims classified runs under a three-minute renewed lease, with up to three retries per step.

One place I deviated from Anthropic’s guide for this workflow is sessions. Their article lets a run stay inside a long-lived session that carries context forward. In nday, every agent call starts in a fresh session. The only state that crosses step boundaries is structured step output and files stored under memory/<repo>/ (notes, findings, reports, saved tools like the build recipe, and an index.json). That keeps context small and prevents an earlier agent’s bad assumption from biasing a later verification step.

Tool access is isolated the same way. Every tool-using agent call gets its own scoped nday mcp server exposing only the allowlisted tools for its role. Claude’s built-in tools are turned off, and Codex runs with its own shell, browser, and web search disabled, so agents can only act through nday.

The outbox and dreaming steps are wired up but minimal. The outbox inserts each report row in the same Postgres transaction as the terminal checkpoint and writes markdown files to disk, with no external notification channel yet. The daily dreaming pass uses Sonnet to distill saved notes into per-module and per-CWE patterns once finished runs accumulate.

Running on boat.dev

The first full run worked on my Mac and immediately exposed a disk problem. I was down to 29 GB free out of 460 GB, with nday eating about 70 GB across build artifacts, CodeQL databases, and 25 GB of Docker Desktop. Every classified commit left behind 3 to 4 GB of checkouts, compiled artifacts, and graph databases. Running a 200-commit eval locally would have needed 600 GB or more, larger than the biggest VM disk available.

Moving execution to boat.dev solved the disk problem and gave me the cleanest security boundary in the system. boat.dev rents root Ubuntu VMs with SSH and Docker that you can fork from a prepared base image. My base-image setup switches Docker to rootless mode so container-written files do not break git clean. nday forks one fresh VM per classified run and deletes it when the run ends, keeping disk usage flat no matter how many commits come through.

Just as importantly, the agents themselves never move to the VM. The Claude and Codex CLIs, their logins, Postgres, saved repo files, and triage stay on my Mac. Only the untrusted work (checkouts, builds, live target servers, the exploit sandbox, and CodeQL) lives on the VM. nday forks each machine with boat fork --no-env so no stored account secrets ever land on it, and sends tool commands over SSH. Even if an untrusted commit or an exploit payload escaped its container, there are no API keys or logins on that VM to steal.

Because every VM is disposable, nday runs multiple commits concurrently, three by default (nday serve --vms N). On boat’s default tier (4 vCPU, 8 GB RAM), full end-to-end runs take roughly 65 to 90 minutes, and three commits running in parallel across three VMs finished in 1 hour 18 minutes.

How the Agents Work Together

Each step is a CLI call (claude -p or codex exec) with a role prompt and a narrow toolset. Three models cover all ten roles:

I split vendors on verification by preference: Codex (gpt-5.6-sol, high effort, Daybreak Blue) writes exploits and bypasses, while Claude Opus acts as the PoC judge, so the same model family is not grading its own exploit.

Triage: Screen and Classifier (Steps 2 and 3)

The commit screen gets only the commit message, changed file list, and diff, with no tools. Its job is cheap filtering: drop pure documentation changes that have nothing to do with security, and pass anything questionable along. Pure dependency-version bumps are dropped deterministically in Go before the classifier runs.

The classifier sees the commit messages (plus the GitHub PR title and description when available), the diff, and read-only repo tools (read_file, read_file_before_fix, search_code, read_diff, list_changed_files). To flag a commit, it has to name a concrete attack: who the attacker is, what input they send to which entry point, and what they gain. Its prompt warns it not to trust commit prose: “Commit messages often hide security fixes (‘improve validation’, ‘fix NPE’, an issue number only). Judge the code, not the message.”

Today the classifier runs a single Opus vote with those repo tools. A confident yes or no finishes in one call. Only borderline calls (probability of yes in [0.20, 0.70)) trigger two extra votes, where any split marks the commit unsure and sends it on to the build. I would rather spend a disposable VM on an occasional false alarm than drop a real security fix before it ever reaches the build. I did not start with that setup; Tuning the Classifier with Evals covers why benchmarks pushed me away from blind multi-voting.

Building the Target and Tracing It with CodeQL (Step 4)

Because every open-source repository has its own build quirks, nday uses a dedicated environment builder agent. It reads the repo’s build files and writes a JSON recipe covering the build image, dependency resolution, full build command, backing services (such as Postgres), and health checks. A recipe only counts once try_recipe actually builds, starts, and health-checks a commit.

Once verified, nday records the recipe to disk under the repo’s saved tools directory and reuses it to build both the parent and fix commits. In most runs the saved recipe works with zero model calls. When an older commit recently hit upstream tooling drift, the environment builder stepped in automatically, adjusted the build flags, and recorded the updated recipe.

Because CodeQL traces the build to produce a queryable code graph, the recipe has to compile the whole repository rather than a subset of modules. I started this layer on Joern and switched to CodeQL after a head-to-head test on the main project: Joern only followed static calls and found no entry point for two of three test fixes, while CodeQL followed virtual dispatch and resolved entry points for both.

Proving Instead of Claiming: Analyzer, FP Check, Exploit, and PoC Judge (Steps 5 and 6)

Once both servers and graphs are ready, the analyzer reads the diff and code graph to write a structured hypothesis: source, sink, missing check, and reproduction plan.

Before launching the exploit agent, nday runs a deterministic CodeQL false-positive check on the parent commit’s graph, with no LLM involved, based on Trail of Bits’ fp-check skill. It checks whether an entry point reaches the affected methods and sinks the analyzer named and looks for unsanitized data flow from attacker input. A run is only dismissed when those methods exist in the graph, no entry point reaches them within six hops, and the reverse search was not cut short. Anything inconclusive moves on to live exploitation, which settles reachability directly.

The exploit agent works inside an isolated Docker sandbox with no internet access. It can reach only the two live servers, plus an optional Playwright browser container when a bug requires a browser to trigger. Its output is a self-contained exploit program with a README that reads TARGET_URL from the environment and exits 0 when it observes the security effect or 1 when blocked.

That rerun gate is how nday avoids generating the kind of broken LLM PoCs Google warned about. nday copies the exploit out of the sandbox, starts fresh, empty-state parent and fix servers, and reruns the program itself. Only exit 0 on the parent and exit 1 on the fix advances. Then the Opus PoC judge inspects the exploit files, the code, and nday’s rerun output, checks the target, authorization checks, and observed effect, and must rule the exploit proven in two independent calls.

Checking Whether the Fix Closed the Class: Blast Radius, Bypass, and Report (Steps 7–9)

Confirming the original bug is only half the point. On every confirmed fix, the blast-radius agent, inspired by Trail of Bits’ variant-analysis skill, queries the fixed code graph for sibling sinks and other paths that should carry the new guard but do not.

The bypass agent then gets 15 minutes against the patched server inside the same sandbox (with shell and browser) to prove either a fix bypass (defeating the patch’s own check) or a variant (hitting the same bug class through untouched code). Every claim goes through the exact same fresh-server rerun and double Opus judge gate. Finally, Sonnet writes the report while keeping agent claims separate from proven outcomes, and nday appends the raw rerun and judge verdicts directly from code.

Tuning the Classifier with Evals

Because everything downstream of triage burns around an hour of cloud compute, the classifier is the highest-leverage component in the pipeline. Rather than guessing at prompt tweaks, I built benchmarks across multiple open-source projects, combining advisory-linked fixes, audited silent fixes, and hard non-security negatives with CVE IDs and issue links stripped out so the model had to judge the code itself, and hill-climbed the classifier against them.

Running those evals changed how I tuned it. Adding prompt rules to fix one tricky commit often broke another, and run-to-run variance was large enough that chasing small dev-set score changes was mostly noise. What actually improved accuracy was giving the classifier tools to read surrounding code and grouping multi-commit PRs so isolated cleanup commits are not judged out of context.

Once the classifier could inspect the repo, a single Opus vote matched blind three-voting at roughly half the cost, with borderline confidence scores cleanly isolating the small set of commits worth a second look. That finding is what drove nday’s current 1-vote plus grey-zone design.

On a side note, the exploit agent deserves the same benchmark-and-tune loop. Right now it is validated through end-to-end runs on hand-picked fixes rather than a large held-out exploit benchmark, and building that eval harness is planned for a later update.

Results

I ran nday across hand-picked commits from the main Java project, wrapping up with a 9-commit end-to-end run on the updated 1-vote and gpt-5.6-sol pipeline. Across those runs, nday confirmed eight security fixes by live exploit, covering token validation, OAuth grant checks, rate limiting, concurrency races, session handling, and delegated-admin privilege escalation. In the 9-commit batch alone, it confirmed all six security commits and filtered out all three non-security commits (one docs-only skip, one deterministic dependency-bump drop, and one single-vote no).

Two findings stood out beyond basic confirmation. First, one of the eight confirmed fixes, a password-reset rate limit, had no CVE or advisory anywhere: a silent fix the classifier caught straight from the diff. Second, two of the eight patches were incomplete. In both cases the fix held on the specific path it targeted, so no agent bypassed a fix’s own check directly, but blast-radius analysis and the bypass agent proved live variants on untouched sibling paths on the patched servers (an alternate OAuth grant handler missing the same token-endpoint check, and four other email-sending flows missing the same cooldown).

Takeaways and What’s Next

The biggest takeaway from building nday is to give every agent a deterministic way to verify its own work, and to avoid letting the same model family grade its own exploit. Everything an agent reports before a clean rerun and an independent check is still just a hypothesis. For teams shipping open-source code or public SDKs, running a verified loop like this in your own release workflow beats waiting for someone else to run exploit_agent against your commit history.

Right now nday runs end-to-end on Java repositories, with outbox notifications queued up next. There is also a bigger scope boundary to keep in mind: while nday works against repositories where source code is public, attackers are already taking a similar agentic approach against compiled binaries, diffing binary patches to recover vulnerabilities and generate exploits where no source exists at all. That brings a different set of tooling and challenges, and it is something I plan to cover in a later post.
